Objective

In this lab, you will build a complete STM32 embedded development environment from scratch on your laptop, then hand-assemble a bare HAL/CMSIS firmware project for the NUCLEO-L496ZG-P development board without using STM32CubeMX's graphical Pinout/Project-Generator interface. You will install the STM32CubeIDE for VS Code extension pack, which brings a full C/C++ editing, build, flash, and debug experience directly into Visual Studio Code, and its built-in Bundle Manager will automatically download the ARM compiler, debugger, and programmer the first time your project needs them. You will obtain ST's official CMSIS and HAL driver source directly from the STM32CubeL4 firmware package, wire together your own CMakeLists.txt, linker script, and startup file, and write every peripheral initialization call — clocks, GPIO, and UART — yourself in main.c by reading the HAL header files directly. You will then write a simple verification program that blinks an LED and streams data over a UART serial connection, and confirm end-to-end operation by observing both the physical LED and a serial terminal on your laptop.

By the end of this lab you will be able to: assemble a bare-metal STM32 project directly from ST's CMSIS and HAL source libraries (no code generator involved), write clock, GPIO, and UART initialization code by hand using the HAL API, build and flash firmware entirely within VS Code, and interpret live serial output from the target board.

  • NUCLEO-L496ZG-P Development Board
  • USB Type-A to Micro-USB Cable (for the on-board ST-LINK programmer)
  • Laptop running Windows 10 or Windows 11 (64-bit)
  • Internet connection (for downloading tools and firmware packages)

Background

The STM32 Ecosystem

STMicroelectronics produces one of the most widely used families of 32-bit microcontrollers in industry: the STM32 series. These devices are built on ARM Cortex-M cores and span an enormous range of performance and power profiles. ST normally encourages developers to use STM32CubeMX, a graphical tool that lets you select a board, drag-and-drop configure its pins and peripherals, and automatically generate a ready-to-compile project. This course intentionally skips that graphical configurator. Understanding what CubeMX generates on your behalf — clock trees, GPIO alternate-function mappings, HAL init sequences — is the entire point of an embedded systems course, so in this lab you will pull the same underlying CMSIS/HAL source libraries ST ships and wire a project together, and initialize every peripheral, by hand.

  • STM32CubeMX – Used in this lab only as a package-download manager to fetch the STM32CubeL4 firmware package (CMSIS headers and HAL driver source) onto your machine. You will not create a project or touch its Pinout/Configuration GUI.
  • STM32CubeIDE for VS Code – ST's official extension pack for Visual Studio Code, and the direct successor to the older "STM32 VS Code Extension." It drives the CMake build and can flash or debug the board directly from the editor. Rather than requiring a separate STM32CubeCLT command-line tools installer, it includes a Bundle Manager that automatically downloads the exact ARM cross-compiler (arm-none-eabi-gcc), CMake, Ninja, and flashing/debugging tools your project needs, an ST-provided debug adapter for ST-LINK and J-Link probes, a clangd-based C/C++ editor, and a built-in serial terminal — all as one installable pack.

The NUCLEO-L496ZG-P Development Board

The NUCLEO-L496ZG-P is a Nucleo-144 format evaluation board built around the STM32L496ZGT6P microcontroller. Key hardware facts you will rely on in this lab:

  • Core: ARM Cortex-M4 with FPU, running up to 80 MHz.
  • Memory: 1 MB Flash, 320 KB SRAM.
  • On-board ST-LINK/V3E: An integrated programmer/debugger that connects to your laptop over a single Micro-USB cable. It appears on your PC as a virtual COM port (for serial output) and as a programmable debug interface (for flashing and stepping through code) — no external programmer is needed.
  • User LEDs: Three user-controllable LEDs — LD1 (green, PC7), LD2 (blue, PB7), and LD3 (red, PB14) — each a simple push-pull GPIO output. You will configure these pins yourself.
  • User Push-Button (B1): A tactile button connected to PC13 with an external pull-up resistor.
  • Virtual COM Port (VCP): USART3 on PD8 (TX) / PD9 (RX), alternate function AF7, is wired directly to the ST-LINK, so data you transmit with HAL_UART_Transmit() appears in a serial terminal on your laptop without any additional hardware.

Board Orientation Note: The NUCLEO-L496ZG-P has two USB connectors. The Micro-USB port labeled "USB ST-LINK" (CN1) is the one used for programming and the virtual COM port. The second USB connector is for the STM32's own USB peripheral and is not used in this lab. Always plug the ST-LINK port into your laptop.

Hardware Abstraction Layer (HAL)

The STM32 HAL (Hardware Abstraction Layer) is a C library maintained by STMicroelectronics. It wraps every on-chip peripheral — GPIOs, UARTs, SPI buses, DMA controllers, timers, and more — behind a consistent, device-independent API. This means that code written with HAL_GPIO_TogglePin() will compile and behave correctly on an L496, an F4, an H7, or any other STM32 device with only minor project-level changes.

Normally CubeMX generates HAL initialization calls automatically based on a graphical peripheral configuration. In this lab you skip that step entirely: you will call HAL_GPIO_Init(), HAL_UART_Init(), and HAL_RCC_OscConfig() yourself directly in main.c, using the parameter values and macro names documented in each HAL header file (stm32l4xx_hal_gpio.h, stm32l4xx_hal_uart.h, etc.). This is exactly the code CubeMX would have written for you — you are simply the one writing it.

CMake Build System

CMake is an industry-standard, cross-platform build system generator. In this lab you will write your own CMakeLists.txt that describes your source files, include paths, compiler flags, and linker script. The STM32CubeIDE for VS Code extension pack (through its bundled Microsoft CMake Tools component) reads this file to drive the actual compilation with arm-none-eabi-gcc, using the compiler that the extension's Bundle Manager downloads for you.

Where the Library Source Comes From

ST publishes the CMSIS device headers and HAL driver source for every STM32 family as the STM32CubeL4 firmware package. You will fetch this package once, using STM32CubeMX purely as a download manager (its Manage embedded software packages menu), and then copy the following pieces directly into your own hand-built project folder:

  • Drivers/CMSIS — ARM Cortex-M core headers and the STM32L4 device header/register definitions (stm32l496xx.h, etc.), plus the GCC startup assembly file for your exact part number.
  • Drivers/STM32L4xx_HAL_Driver — the HAL source (.c) and header (.h) files for every peripheral, including stm32l4xx_hal_gpio.c and stm32l4xx_hal_uart.c, which you will call directly.
  • A stock linker script and hal_conf.h configuration header for the NUCLEO-L496ZG-P, taken from ST's bare Templates reference project — these are boilerplate chip bring-up files, not peripheral configuration, so you copy them as-is rather than generating them.

6. Assemble a Bare HAL Project by Hand

This is the step that replaces STM32CubeMX's project generator. You will create every file yourself, copying only the vendor CMSIS/HAL source and the minimum chip bring-up boilerplate (linker script, startup file, HAL feature-config header) from the firmware package you downloaded in Step 5. Everything that touches a peripheral — clocks, GPIO, UART — you write from scratch in Step 9.

6a. Create the Folder Skeleton

  1. Choose a project folder, e.g. C:\Users\YourName\STM32Projects\Lab1_NUCLEO_L496\. Avoid paths with spaces or special characters.
  2. Inside it, create the following empty folders: Core\Inc, Core\Src, Core\Startup, Drivers, and cmake. You should end up with: 
    Lab1_NUCLEO_L496/
├── CMakeLists.txt              ← you will write this (6f)
├── STM32L496ZGTX_FLASH.ld      ← copied from the firmware package (6c)
├── cmake/
│   └── gcc-arm-none-eabi.cmake ← you will write this (6f)
├── Core/
│   ├── Inc/                    ← main.h, stm32l4xx_it.h, stm32l4xx_hal_conf.h
│   ├── Src/                    ← main.c, stm32l4xx_it.c, system_stm32l4xx.c
│   └── Startup/                ← startup_stm32l496xx.s
└── Drivers/
    ├── CMSIS/                  ← copied wholesale from the firmware package (6b)
    └── STM32L4xx_HAL_Driver/   ← copied wholesale from the firmware package (6b)

6b. Copy the CMSIS and HAL Driver Source

STM32CubeMX's package manager (Step 5) downloaded the firmware package to a local repository cache, typically C:\Users\YourName\STM32Cube\Repository\STM32Cube_FW_L4_Vx.x.x\.

  1. From that cache folder, copy the entire Drivers\CMSIS folder into your project's Drivers\CMSIS.
  2. Copy the entire Drivers\STM32L4xx_HAL_Driver folder into your project's Drivers\STM32L4xx_HAL_Driver. This gives you stm32l4xx_hal_gpio.c/.h, stm32l4xx_hal_uart.c/.h, stm32l4xx_hal_rcc.c/.h, and every other HAL module — the exact same source CubeMX would have copied for you.

6c. Copy the Startup File and Linker Script

  1. Copy Drivers\CMSIS\Device\ST\STM32L4xx\Source\Templates\gcc\startup_stm32l496xx.s into your project's Core\Startup\ folder. This is the CMSIS-provided reset/interrupt vector table and reset handler for the exact L496 part — low-level chip bring-up code, not peripheral configuration, so you copy it rather than author it.
  2. Copy Projects\NUCLEO-L496ZG-P\Templates\STM32CubeIDE\STM32L496ZGTX_FLASH.ld from the firmware package into the root of your project folder. This linker script describes the L496's 1 MB Flash and 320 KB SRAM memory map.

6d. Copy the System Init File and HAL Configuration Header

  1. Copy Projects\NUCLEO-L496ZG-P\Templates\Src\system_stm32l4xx.c into your project's Core\Src\. This provides SystemInit(), which the startup file calls before main() to enable the FPU and set the vector table location.
  2. Copy Projects\NUCLEO-L496ZG-P\Templates\Inc\stm32l4xx_hal_conf.h into your project's Core\Inc\. This header simply lists which HAL modules to compile in (GPIO, UART, RCC, CORTEX, etc. are already enabled by default) and defines oscillator frequency constants — it is build configuration, not pin/peripheral configuration.

6e. Write main.h and the Interrupt Handler File

  1. Create Core\Inc\main.h with the following minimal content: 
    #ifndef __MAIN_H
#define __MAIN_H

#include "stm32l4xx_hal.h"

#endif /* __MAIN_H */
  2. Create Core\Inc\stm32l4xx_it.h: 
    #ifndef __STM32L4xx_IT_H
#define __STM32L4xx_IT_H

void SysTick_Handler(void);

#endif /* __STM32L4xx_IT_H */
  3. Create Core\Src\stm32l4xx_it.c. The startup file already provides a weak default (empty, infinite-loop) handler for every interrupt, but HAL_Delay() needs the SysTick handler to actually advance the HAL's millisecond tick counter, so you must override it: 
    #include "main.h"
#include "stm32l4xx_it.h"

void SysTick_Handler(void)
{
  HAL_IncTick();
}
    Without this, HAL_Delay() and HAL_GetTick() would never return — every millisecond tick interrupt would hit the vector table's default handler and spin forever instead of incrementing the counter the HAL relies on.

6f. Write CMakeLists.txt and the Toolchain File

  1. Create cmake\gcc-arm-none-eabi.cmake: 
    set(CMAKE_SYSTEM_NAME Generic)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(CMAKE_C_COMPILER   arm-none-eabi-gcc)
set(CMAKE_ASM_COMPILER arm-none-eabi-gcc)
set(CMAKE_OBJCOPY      arm-none-eabi-objcopy)
set(CMAKE_SIZE         arm-none-eabi-size)

set(CMAKE_TRY_COMPILE_TARGET_TYPE STATIC_LIBRARY)

set(CPU_FLAGS "-mcpu=cortex-m4 -mthumb -mfpu=fpv4-sp-d16 -mfloat-abi=hard")
set(CMAKE_C_FLAGS   "${CPU_FLAGS} -Wall -ffunction-sections -fdata-sections")
set(CMAKE_ASM_FLAGS "${CPU_FLAGS}")
set(CMAKE_EXE_LINKER_FLAGS "${CPU_FLAGS} -specs=nano.specs -Wl,--gc-sections")
    This tells CMake to cross-compile for a Cortex-M4 with a hardware FPU using the compiler the Bundle Manager will download in Step 7, instead of your host machine's own compiler.
  2. Create CMakeLists.txt in the project root: 
    cmake_minimum_required(VERSION 3.20)

set(CMAKE_TOOLCHAIN_FILE ${CMAKE_SOURCE_DIR}/cmake/gcc-arm-none-eabi.cmake)

project(Lab1_NUCLEO_L496 C ASM)

add_executable(${PROJECT_NAME}
    Core/Src/main.c
    Core/Src/stm32l4xx_it.c
    Core/Src/system_stm32l4xx.c
    Core/Startup/startup_stm32l496xx.s

    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_cortex.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_rcc.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_rcc_ex.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_gpio.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_uart.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_uart_ex.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_pwr.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_pwr_ex.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_flash.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_flash_ex.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_dma.c
    Drivers/STM32L4xx_HAL_Driver/Src/stm32l4xx_hal_exti.c
)

target_include_directories(${PROJECT_NAME} PRIVATE
    Core/Inc
    Drivers/CMSIS/Include
    Drivers/CMSIS/Device/ST/STM32L4xx/Include
    Drivers/STM32L4xx_HAL_Driver/Inc
)

target_compile_definitions(${PROJECT_NAME} PRIVATE
    STM32L496xx
    USE_HAL_DRIVER
)

target_link_options(${PROJECT_NAME} PRIVATE
    -T${CMAKE_SOURCE_DIR}/STM32L496ZGTX_FLASH.ld
    -Wl,-Map=${PROJECT_NAME}.map
)

add_custom_command(TARGET ${PROJECT_NAME} POST_BUILD
    COMMAND ${CMAKE_SIZE} $
)
    Every source file listed here is one you either copied from the firmware package or will write yourself in the next steps — there is no generated file anywhere in this list.

  1. Create a minimal Core\Src\main.c for now, just to prove the toolchain works:

{

  {
  }
}
  2. Click the STM32Cube icon in the left Activity Bar, then click Build. Alternatively, press Ctrl+Shift+P, run CMake: Build.
  3. A successful build ends with a message similar to:

9. Write the Verification Firmware

Now write the real main.c by hand: configure the system clock, initialize GPIO for the LEDs, initialize USART3, then blink LD1 and stream a status message once per second. There are no USER CODE markers in this project because there is no generator to preserve code from — the entire file is yours.

  1. Open Core\Src\main.c and replace its contents with the includes, handle, and clock configuration below: 
    #include "main.h"
#include <stdio.h>
#include <string.h>

UART_HandleTypeDef huart3;

static uint32_t seconds_elapsed = 0;
static char     uart_buf[80];

/* Configures SYSCLK = 80 MHz using the MSI-driven PLL (MSI=4MHz, PLLM=1,
 * PLLN=40, PLLR=2). This is the standard 80 MHz recipe ST documents for
 * this device; you would normally never need to touch this again. */
static void SystemClock_Config(void)
{
  RCC_OscInitTypeDef RCC_OscInitStruct = {0};
  RCC_ClkInitTypeDef RCC_ClkInitStruct = {0};

  RCC_OscInitStruct.OscillatorType = RCC_OSCILLATORTYPE_MSI;
  RCC_OscInitStruct.MSIState = RCC_MSI_ON;
  RCC_OscInitStruct.MSIClockRange = RCC_MSIRANGE_6;
  RCC_OscInitStruct.MSICalibrationValue = RCC_MSICALIBRATION_DEFAULT;
  RCC_OscInitStruct.PLL.PLLState = RCC_PLL_ON;
  RCC_OscInitStruct.PLL.PLLSource = RCC_PLLSOURCE_MSI;
  RCC_OscInitStruct.PLL.PLLM = 1;
  RCC_OscInitStruct.PLL.PLLN = 40;
  RCC_OscInitStruct.PLL.PLLR = 2;
  RCC_OscInitStruct.PLL.PLLP = 7;
  RCC_OscInitStruct.PLL.PLLQ = 4;
  if (HAL_RCC_OscConfig(&RCC_OscInitStruct) != HAL_OK)
  {
    while (1);
  }

  RCC_ClkInitStruct.ClockType = RCC_CLOCKTYPE_SYSCLK | RCC_CLOCKTYPE_HCLK |
                                 RCC_CLOCKTYPE_PCLK1 | RCC_CLOCKTYPE_PCLK2;
  RCC_ClkInitStruct.SYSCLKSource = RCC_SYSCLKSOURCE_PLLCLK;
  RCC_ClkInitStruct.AHBCLKDivider = RCC_SYSCLK_DIV1;
  RCC_ClkInitStruct.APB1CLKDivider = RCC_HCLK_DIV1;
  RCC_ClkInitStruct.APB2CLKDivider = RCC_HCLK_DIV1;
  if (HAL_RCC_ClockConfig(&RCC_ClkInitStruct, FLASH_LATENCY_4) != HAL_OK)
  {
    while (1);
  }
}
    This yields an 80 MHz system clock — the maximum for the L496 — matching the value CubeMX would have selected by default.
  2. Below SystemClock_Config(), add the GPIO and UART init functions you are writing by hand, using the pin table from the Background section (LD1 = PC7, USART3 = PD8/PD9 on AF7): 
    static void LED_GPIO_Init(void)
{
  GPIO_InitTypeDef GPIO_InitStruct = {0};

  __HAL_RCC_GPIOC_CLK_ENABLE();

  GPIO_InitStruct.Pin   = GPIO_PIN_7;              /* LD1 (green) on PC7 */
  GPIO_InitStruct.Mode  = GPIO_MODE_OUTPUT_PP;
  GPIO_InitStruct.Pull  = GPIO_NOPULL;
  GPIO_InitStruct.Speed = GPIO_SPEED_FREQ_LOW;
  HAL_GPIO_Init(GPIOC, &GPIO_InitStruct);
}

static void USART3_UART_Init(void)
{
  GPIO_InitTypeDef GPIO_InitStruct = {0};

  __HAL_RCC_GPIOD_CLK_ENABLE();
  __HAL_RCC_USART3_CLK_ENABLE();

  GPIO_InitStruct.Pin       = GPIO_PIN_8 | GPIO_PIN_9;  /* PD8=TX, PD9=RX */
  GPIO_InitStruct.Mode      = GPIO_MODE_AF_PP;
  GPIO_InitStruct.Pull      = GPIO_NOPULL;
  GPIO_InitStruct.Speed     = GPIO_SPEED_FREQ_VERY_HIGH;
  GPIO_InitStruct.Alternate = GPIO_AF7_USART3;
  HAL_GPIO_Init(GPIOD, &GPIO_InitStruct);

  huart3.Instance          = USART3;
  huart3.Init.BaudRate     = 115200;
  huart3.Init.WordLength   = UART_WORDLENGTH_8B;
  huart3.Init.StopBits     = UART_STOPBITS_1;
  huart3.Init.Parity       = UART_PARITY_NONE;
  huart3.Init.Mode         = UART_MODE_TX_RX;
  huart3.Init.HwFlowCtl    = UART_HWCONTROL_NONE;
  huart3.Init.OverSampling = UART_OVERSAMPLING_16;
  if (HAL_UART_Init(&huart3) != HAL_OK)
  {
    while (1);
  }
}
    Notice there is no separate MSP file — you enabled the GPIOC/GPIOD/USART3 peripheral clocks and configured the pins directly, in the same function, before calling HAL_UART_Init(). CubeMX would have split this across main.c and stm32l4xx_hal_msp.c; here it is all in one place so you can see exactly what has to happen and in what order.
  3. Finally, write main() itself: 
    int main(void)
{
  HAL_Init();
  SystemClock_Config();
  LED_GPIO_Init();
  USART3_UART_Init();

  const char *startup_msg =
      "\r\n==============================\r\n"
      "  ECGR-4101 Lab 1 Verification \r\n"
      "  NUCLEO-L496ZG-P Ready        \r\n"
      "==============================\r\n";
  HAL_UART_Transmit(&huart3, (uint8_t *)startup_msg,
                    strlen(startup_msg), HAL_MAX_DELAY);

  while (1)
  {
    /* Toggle the green user LED (LD1) */
    HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_7);

    /* Format a status message and send it over USART3 */
    int msg_len = snprintf(uart_buf, sizeof(uart_buf),
                           "Lab 1 OK  |  t = %4lu s  |  LD1 = %s\r\n",
                           seconds_elapsed,
                           HAL_GPIO_ReadPin(GPIOC, GPIO_PIN_7) ? "ON " : "OFF");
    HAL_UART_Transmit(&huart3, (uint8_t *)uart_buf,
                      (uint16_t)msg_len, HAL_MAX_DELAY);

    seconds_elapsed++;

    /* Wait 1000 ms before the next iteration */
    HAL_Delay(1000);
  }
}
  4. Press Ctrl+S to save main.c.

Code explanation:

  • HAL_GPIO_TogglePin(GPIOC, GPIO_PIN_7) — Reads the current output latch of PC7 and writes the opposite value, toggling LD1 between on and off with each call. Ctrl+Click into stm32l4xx_hal_gpio.h to see this and the other GPIO functions available to you.
  • snprintf(uart_buf, sizeof(uart_buf), ...) — Safely formats a string into uart_buf without risking a buffer overflow. It returns the number of characters written, which we store in msg_len and pass to HAL_UART_Transmit() so the HAL knows exactly how many bytes to send.
  • HAL_Delay(1000) — Puts the processor into a busy-wait loop for exactly 1000 milliseconds, producing a 1 Hz LED toggle rate and one UART message per second.

  4. Click the Connect / Start (play ►) button in the serial terminal toolbar. The terminal will open the port and begin listening.

14. Checkpoint: Exploring the HAL Source You Used

Before finishing the lab, spend a few minutes exploring the library code you called from main.c. Understanding this structure is foundational to all future labs in this course.

  1. In the VS Code Explorer, open Drivers → CMSIS → Device → ST → STM32L4xx → Include → stm32l496xx.h and search for GPIOC_BASE. This is the raw register base address that GPIOC (used in your HAL_GPIO_Init() call) ultimately expands to — the same value you would have had to look up in the reference manual if you were writing bare-register code instead of using the HAL.
  2. Open Drivers → STM32L4xx_HAL_Driver → Src → stm32l4xx_hal_gpio.c. Browse to the HAL_GPIO_TogglePin() function definition. Observe how the HAL translates a high-level function call into a single write to the GPIO port's BSRR (Bit Set/Reset Register) — this is the kind of hardware detail the HAL abstracts away from your application code.
  3. Open Drivers → STM32L4xx_HAL_Driver → Src → stm32l4xx_hal_uart.c and find HAL_UART_Init(). Compare its parameter validation and register-write sequence against the huart3.Init fields you set by hand in Step 9 — every field you filled in corresponds directly to a register field this function configures.
